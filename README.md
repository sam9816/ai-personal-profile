# AI 个人档案 · ai-personal-profile

> 一份**可版本化的跨 AI 共享个人上下文档案**。把「我是谁、我怎么工作、我偏好什么」沉淀为单一事实源（Single Source of Truth），供不同 AI 客户端、Agent、IDE 插件读取，避免每次对话重复交代背景。

| 项目 | 内容 |
| --- | --- |
| 仓库用途 | 跨 AI 工具共享的个人档案 |
| 可见性 | Public（公开仓库） |
| 档案入口 | 本文件 `README.md` |
| 当前版本 | v0.1.1 |
| 最后更新 | 2026-11-05 |
| 维护方式 | Git 版本记录 + Issues 待办跟踪 |
| 变更记录 | [CHANGELOG.md](CHANGELOG.md) |

> ⚠️ **公开仓库提醒**：本仓库内容任何人可见、可被搜索引擎与 AI 抓取，且历史提交不可真正抹除。只写「愿意被公开引用的偏好与事实」，不要写入手机号、私人邮箱、住址、证件号、账号密码、API Key、公司内部数据、未公开项目细节。详见 [隐私与合规提示](docs/隐私与合规提示.md)。

## 快速开始

1. **填充**：按下方六章节逐条替换 `[示例]` 条目。每条尽量一句话、可验证、可引用；建议标注生效日期，过期条目及时删除而不是堆在末尾。
2. **引用**：在任意 AI 工具中让 Agent 读取 RAW 地址（把 `sam9816` 换成你的 GitHub 用户名）：
   ```
   https://raw.githubusercontent.com/sam9816/ai-personal-profile/main/README.md
   ```
   也可以直接把本文件内容粘贴进 AI 的「自定义指令 / 个人记忆 / System Prompt」区域。
3. **留痕**：每次修改都提交并写清改动原因，重要版本打 tag。规范见 [版本管理约定](docs/版本管理约定.md)。
4. **同步**：推送后在各 AI 端重新拉取，保证多端读到同一版本；版本号以 `CHANGELOG.md` 与 tag 为准。
5. **追踪**：待补充、待核实、待同步的事项开 Issue，用标签管理；看板配置见 [Projects 搭建说明](.github/PROJECT_SETUP.md)。

## 档案内容

> **说明**：以下全部为占位示例，仅用于示范条目粒度与写法。请逐条替换为自己的内容，并删除 `[示例]` 标记。示例刻意保持泛化，未包含任何真实个人信息。

### 1. 个人简介与背景

*写什么：所在领域、经验年限、角色定位、时区与语言等相对稳定的事实。*

- **[示例]** 领域背景：某行业从业 5 年，覆盖多个细分方向
- **[示例]** 角色定位：同时承担内容生产与流程/工具设计两类工作
- **[示例]** 语言与时区：中文为主、偶用英文；按 UTC+8 安排默认时间

### 2. 工作与学习习惯

*写什么：任务拆解方式、信息输入习惯、对交付节奏的要求。*

- **[示例]** 先提供参考材料，再让 AI 产出；不接受凭空补细节
- **[示例]** 长任务拆成编号步骤，每步有明确产出物
- **[示例]** 结论先行，论据随后，末尾附下一步建议

### 3. 沟通风格偏好

*写什么：语气、详略、结构化程度、明确不希望出现的行为。*

- **[示例]** 语气：沉稳、直接；不使用寒暄与空泛赞美
- **[示例]** 输出结构：表格 / 编号清单 / 进度条，避免大段连续文字
- **[示例]** 禁止项：不猜测未提供的信息；不确定时先查证再提问

### 4. 常用工具与技术栈

*写什么：实际在用的 AI 客户端、文档与协作工具、版本管理与自动化方式。*

- **[示例]** AI 客户端：若干云端助手 + 一个本地模型（按实际填写）
- **[示例]** 文档协作：Markdown、Office/WPS、在线文档
- **[示例]** 版本管理：Git + GitHub，提交信息遵循 Conventional Commits

### 5. 项目经验与成果

*写什么：一句话一个项目，尽量带角色与可量化结果；只写可公开部分。*

- **[示例]** 项目 A｜角色：负责人｜成果：交付 N 份标准化文档并复用
- **[示例]** 项目 B｜角色：参与者｜成果：某流程耗时由 X 降至 Y
- **[示例]** 沉淀物：可复用模板 / SOP / 检查清单各 1 套

### 6. 长期目标

*写什么：带时间尺度的目标，以及档案本身的维护约定。*

- **[示例]** 3 个月内：六章节填满，并被至少 3 个 AI 工具实际引用
- **[示例]** 1 年内：形成「个人上下文 → AI 输出质量」的评估方式
- **[示例]** 持续：每季度复审一次档案，删除过期条目并记录变更原因

**建议的首批种子 Issue**（可用 `scripts/bootstrap-remote.sh` 自动创建）：

1. `填充六章节真实内容`（标签 `profile/fill`, `priority/high`）
2. `在 3 个 AI 客户端中接入 RAW 地址并验证`（标签 `ai/sync`）
3. `季度复审：删除过期条目`（标签 `profile/review`）

> 说明：Issues 可通过仓库设置或 API 直接开启；GitHub Projects 是**账户/组织级对象**，不能由仓库文件自动生成，需按 `PROJECT_SETUP.md` 一次性创建（脚本已含可选步骤）。

## 版本与回溯

Git 天生为每次修改留痕，本仓库额外约定了三层保障：

| 层级 | 机制 | 作用 |
| --- | --- | --- |
| 每次修改 | 一次有意义的 `git commit` + Conventional Commits 信息 | `git log` / `git blame` 可查到「谁在何时为何改了哪行」 |
| 每个阶段 | 语义化 tag（`v0.1.0` → `v0.2.0`）+ `CHANGELOG.md` | 可对比任意两个版本、可一键检出旧版 |
| 远程防护 | 分支保护 + PR 合并 | 避免误推覆盖 main，保留完整评审记录 |

常用命令速查（完整手册见 [版本管理约定](docs/版本管理约定.md)）：

```bash
git log --oneline --graph --decorate       # 查看全部修改历史
git diff v0.1.0 v0.2.0 -- README.md        # 对比两个版本
git revert <commit>                        # 推荐：反向提交回退，历史不丢失
git tag -a v0.2.0 -m "填充沟通偏好章节"    # 打版本标记
```

## 隐私与合规

- 本仓库为**公开**仓库，所有历史版本均可见；敏感信息一旦提交，即使后续删除也仍留在 Git 历史中。
- 引用 RAW 地址意味着把档案内容交给第三方 AI 服务处理，请按该服务的数据使用政策自行判断。
- 不要在档案中写入可识别他人身份的信息、雇主内部信息或任何凭据。
- 若确需记录私密条目，请另建**私有**仓库，公开仓库只保留可公开版本。

详见 [docs/隐私与合规提示.md](docs/隐私与合规提示.md)。
