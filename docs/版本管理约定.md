# 版本管理约定：可追溯、可回退

Git 本身即为版本记录系统，本仓库不需要额外开关。真正要做的是**让每次修改都有意义、有原因、有标记**。本文件是具体操作手册。

---

## 一、三层保障

| 层级 | 机制 | 回答的问题 |
| --- | --- | --- |
| 提交层 | 一次逻辑修改 = 一次 commit，遵循 Conventional Commits | 「这一行为什么被改？」→ `git log` / `git blame` |
| 版本层 | 语义化 tag + `CHANGELOG.md` | 「上个月那版是什么样？」→ `git diff v0.1.0 v0.2.0` |
| 远程层 | 分支保护 + PR | 「能不能被误推覆盖？」→ 强制走评审、留合并记录 |

建议首次推送后在仓库 **Settings → Branches** 为 `main` 添加保护规则：勾选 *Require a pull request before merging*。公开仓库免费可用；脚本 `bootstrap-remote.sh` 也含可选自动配置步骤。

## 二、追溯：查历史

```bash
git log --oneline --graph --decorate --all     # 全部分支与标签的提交图
git log --follow -p -- README.md               # 逐行看 README 的历次改动
git blame README.md                            # 每一行来自哪次提交
git show v0.2.0                                # 查看某个 tag 的提交内容
git tag --list --sort=-version:refname         # 列出所有版本
git diff v0.1.0 v0.2.0 -- README.md            # 对比两个版本差异
```

网页端同样可用：仓库页 **Commits** 看全部历史、文件页 **History** / **Blame** 看单文件演变、**Releases / Tags** 看版本节点。

## 三、回退：三种姿势，别选错

### 1. `git revert` —— 推荐，历史不丢失

适用于**已推送到远程**的修改。它会新建一个「反向提交」，所有人都能看到「做过什么、又撤回了什么」。

```bash
git revert <commit-hash>                       # 生成反向提交
git push origin main
```

### 2. `git reset` —— 仅限本地、尚未推送

会**抹掉**目标之后的提交，已推送的历史绝不要用 `--hard` 强推。

```bash
git reset --soft <commit-hash>                 # 保留改动到暂存区，最温和
git reset --hard <commit-hash>                 # 丢弃之后全部改动，谨慎
```

### 3. 单文件恢复 —— 只想拿回旧版某个文件

```bash
git checkout v0.1.0 -- README.md               # 把 README 恢复到 v0.1.0 的内容
git commit -m "revert: 恢复 README 至 v0.1.0"
```

### 4. 临时查看旧版（不改当前分支）

```bash
git switch --detach v0.1.0                     #  detached HEAD 只读查看
git switch main                                # 看完切回
```

> 回退之后请务必：在 `CHANGELOG.md` 记录回退原因、在对应 Issue 注明、必要时重新打 tag。**不要静默改档。**

## 四、tag 规范

```bash
git tag -a v0.2.0 -m "填充工作习惯与沟通风格章节"   # 附注标签，必带说明
git push origin v0.2.0                              # 推单个 tag
git push origin --tags                               # 推全部 tag
git tag -d v0.2.0                                    # 删除本地 tag
```

- tag 一旦推送即视为已发布，不要复用同一版本号。
- 每个 tag 对应 `CHANGELOG.md` 中一个版本段落，也对应 Projects 看板里的一组已完成 Issue。

## 五、首次推送前必做：修正提交作者

本仓库的初始提交使用了中性占位作者（`Profile Maintainer <profile@localhost>`），因为创建时本机尚未配置 Git 身份。请在首次推送前改成你自己的 GitHub 身份，否则提交不会关联到你的账号：

```bash
git config user.name "你的GitHub用户名"
git config user.email "你的GitHub邮箱或 username@users.noreply.github.com"
git commit --amend --reset-author --no-edit
```

若已经推送过，改写作者属于历史重写，会影响其他克隆，建议接受现状、从下一条提交开始使用正确身份即可。

## 六、误提交敏感信息（重要）

`README.md` 等文件一旦提交并推送到**公开仓库**，即使后续删除，内容仍留在 Git 历史、fork、缓存与搜索引擎中。处置顺序：

1. **立即轮换**泄露的凭据（密码 / Token / API Key），这一步优先于清理仓库。
2. 用 `git filter-repo` 或 BFG 清理历史后强制推送；同时删除相关 tag。
3. 联系 GitHub Support 请求清除缓存视图与 fork 中的残留。
4. 在 `CHANGELOG.md` 记录事件与处置结论，不写泄露内容本身。

预防永远优于处置：提交前对照 [`隐私与合规提示.md`](隐私与合规提示.md) 的检查清单。
